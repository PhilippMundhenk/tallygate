    Approvals

    Requests wait here until you decide or the timeout passes (then they are denied).

    Which button should I use?
    • Allow for 5 min: one operation (an install, a clone). The host is open briefly, so follow-up connections are covered.
    • Allow for … min: a working session with this host — type how many minutes.
    • Allow host permanently (bare IPs) or Allow *.domain permanently (named hosts): a permanent allow rule — exactly this host, or the domain and every subdomain, e.g. all of *.githubusercontent.com. Check the domain line first: github.com.evil.example belongs to evil.example.
    • Deny for … min: refuse and stop asking about this host for a while.
    • Deny permanently: a permanent deny rule, no more prompts.

    All buttons show at once on a wide screen; on a narrow one the … min buttons fold under More. Every decision becomes a normal rule you can review or delete under Destinations. A name you approve is still refused if it resolves into a blocked range (the local network etc.).

    How does local access work?
          
    The form creates a grant for exactly this address and port. The agent requests it with
            tallygate request <name> and you approve each use; edit or delete it on the
            Grants tab.
    
          
    Enter the device's IP address. A name (such as ha.lan) cannot open a blocked range, because
            a name can be pointed anywhere: if you enter one that resolves to a local address, the gateway refuses
            the grant and names the address to enter instead. To keep the name, set it as the host and the address
            as Fixed IP on the Grants tab.
    
          
    To allow a device without a request each time, add an allow rule for its address on Destinations.

    Grants
    
    
    On-request access the agent asks for by name; grants from the config file are read-only here.
    
    
    What is a grant?
      
    A grant is on-request access the agent asks for by name (tallygate request <name>): one or more
        targets (host:port, optionally paths), an access level (read = GET/HEAD/OPTIONS, write = everything)
        and how each use is approved.

    Advanced options
      
    
        
        
        
        
        
        
      
    
      
    What do levels, approval and durations mean?
        
    read allows only GET, HEAD and OPTIONS (no uploads, no WebSockets); write allows
          everything. ask means you approve each request; auto grants it without asking (sensible for read
          on harmless APIs). Durations: 30m, 2h, 1d; the agent may ask for less, never more than the maximum.
    
      
    Targets
    
      
    How do targets work?
        
    https/http targets are inspected per request (method, path, Host). tcp passes raw traffic (write level only).
          A target with an IP address as host, or with a Fixed IP, may be a device on your local network; a target
          that is only a name cannot open a blocked range and is refused when it resolves into one.
          Self-signed certificate? Pin its SHA-256 fingerprint instead of disabling verification.
    
        
      
          
    • Home Assistant API, read-only: http · 192.168.1.20 · 8123 · paths /api/*
      • 
          
    • Proxmox with a self-signed cert: https · pve.lan · 8006 · paths /api2/json/* · fixed IP 192.168.1.30 · fingerprint from
            openssl s_client -connect pve.lan:8006 </dev/null | openssl x509 -noout -fingerprint -sha256
      • 
          
    • SSH to one machine: tcp · 192.168.1.40 · 22 (tcp needs the write level)
      • 
          
    • A public API, only some paths: https · api.example.com · 443 · paths /v1/items/*, /v1/search
      • 
        
    
        
    Paths are globs: * matches any characters including /, so /api/* covers
          /api/states and /api/states/light.kitchen; the query string is not part of the path. Several patterns are comma-separated.
          Fixed IP pins the address instead of resolving the name, and is what lets a named target be a local device.

      • Notifications 
        
        
        
        
        Approval prompts are delivered through the channels below.
        
        
        How are channels set up?
          
        Set up the bot channels (Telegram, Matrix, ntfy, Gotify, Pushover) with Configure: a token you
            save is stored by the control plane and never shown again. Values from the environment keep working;
            what you save here wins. Web Push is set up on this device below. Test sends a sample through a
            channel. Browser notifications also appear for new requests while this tab is in the background.
        
          
        User guide: notification channels
        
        
        
        
        
        
        Notification buttons
        
        
        Choose the decisions a connection request offers in a notification, in the order they are shown.
        
        
        Which buttons does a notification show?
          
        Web Push shows exactly the buttons you choose. Most phones and browsers have room for two,
            so a device shows the first ones in your order and leaves out the rest; tapping the notification
            opens the approvals with every choice. Telegram and Matrix show your buttons first and
            keep the others behind More. ntfy, Gotify and Pushover have no buttons.
        
          
        A button that allows permanently decides from the lock screen what otherwise needs the UI: put it
            first only if you read every request. Allow *.domain permanently names the pattern on the
            button and is left out when a name has no domain of its own. A request for an IP address can only
            be denied from a Web Push notification. Grant requests keep their own buttons.
