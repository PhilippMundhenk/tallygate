    Grant requests

    The agent asks for a predefined bundle of access. The reason it gives is its own unverified claim (flagged on each request), not a checked fact.

    Pending connection requests

    Connections are held until you decide or the timeout passes (then denied). Hard-denied targets (LAN etc.) never appear here.

    Which button should I use?
    • Allow (5 min): one operation (an install, a clone). The host is open briefly, so follow-up connections are covered.
    • Allow (x min…): a working session with this host — type how many minutes.
    • Always (host) (bare IPs) or Always (*.domain) (named hosts): a permanent allow — exactly this host, or the domain and every subdomain, e.g. all of *.githubusercontent.com. Check the domain line first: github.com.evil.example belongs to evil.example.
    • Deny (x min…): refuse and stop asking about this host for a while.
    • Deny (forever): a permanent deny rule, no more prompts.

    All buttons show at once on a wide screen; on a narrow one the … min buttons fold under More. Every decision becomes a normal rule you can review or delete under Destinations. More

    Defined grants
    
    
    On-request access the agent asks for by name. Grants from the config file are read-only here.
    
    
    What a grant is
      
    A grant is on-request access the agent asks for by name (tallygate request <name>): one or more
        targets (host:port, optionally paths), an access level (read = GET/HEAD/OPTIONS, write = everything)
        and how each use is approved. Grants from the config file are read-only here.
    
    
    
    

    
    
      
    New grant
    
      
    
        
        
      
    
      
    
        
        
        
        
      
    
      
      
    This grant uses settings that only Advanced shows
        (several targets, paths, automatic approval, a fixed IP or a pinned certificate). They are kept as they are.
    
      
    Advanced options
      
    
        
        
        
        
        
        
      
    
      
    read allows only GET, HEAD and OPTIONS (no uploads, no WebSockets); write allows
        everything. ask means you approve each request; auto grants it without asking (sensible for read
        on harmless APIs). Durations: 30m, 2h, 1d; the agent may ask for less, never more than the maximum.
    
      
    Targets
    
      
    https/http targets are inspected per request (method, path, Host). tcp passes raw traffic (write level only).
        LAN exempts exactly this target from the hard deny (UI grants only within –).
        Self-signed certificate? Pin its SHA-256 fingerprint instead of disabling verification.
    
      
    Target examples
        
      
          
    • Home Assistant API, read-only: http · ha.lan · 8123 · paths /api/* · LAN
      • 
          
    • Proxmox with a self-signed cert: https · pve.lan · 8006 · paths /api2/json/* · LAN · fingerprint from
            openssl s_client -connect pve.lan:8006 </dev/null | openssl x509 -noout -fingerprint -sha256
      • 
          
    • SSH to one machine: tcp · nas.lan · 22 · LAN (tcp needs the write level)
      • 
          
    • A public API, only some paths: https · api.example.com · 443 · paths /v1/items/*, /v1/search
      • 
        
    
        
    Paths are globs: * matches any characters including /, so /api/* covers
          /api/states and /api/states/light.kitchen; the query string is not part of the path. Several patterns are comma-separated.
          fixed IP pins the address instead of resolving the name.
          Grants guide
    
      
    
      
    
      
      
    Credential injection and disabling TLS verification are only available for grants in the
        gateway config file: a UI session must not be able to send stored secrets to a host of its choosing.
